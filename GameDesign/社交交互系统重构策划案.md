# 社交交互系统重构策划案 (Social Interaction System Overhaul)

## 1. 现状痛点分析 (Current Pain Points)
目前的交互机制本质上是“单体状态机的并联”，而非“系统的串联”，这导致了以下几个核心问题：

*   **单向行为与决策孤立 (One-way Action)**：角色 A 的 AI 目标搜索完全不考虑角色 B 的实时社交意图。当 A 决定和 B 说话时，A 会单方面进入交互状态，而 B 毫无察觉。
*   **状态强制篡改与逻辑断裂 (Forced State Override)**：现有的交互通常通过底层逻辑（如 `settle_behavior_effect`）强行修改目标的 `state`。如果 B 正在做某项高优先级的专注任务（如吃饭、睡觉），会被瞬间强行打断并转头聊天，缺乏自然平滑的过渡和合理性判定。
*   **交互短视/一锤子买卖 (Short-sighted Interaction)**：交互双方仅通过 `target_character_id` 简单链接，一回合结算（加减属性、输出一段文本）后即告结束。无法承载复杂的、多阶段的互动逻辑（如：寒暄 -> 深入探讨 -> 告别），也无法支持需要多轮博弈的玩法（如下棋、打牌、争吵）。
*   **群体社交空白 (Lack of Group Dynamics)**：目前的架构强绑定于 1v1 目标，难以实现 3 人及以上的自然互动（如：多人聚餐、围观讨论、课堂教学）。在旧有实现中，只能靠全屏遍历强行篡改状态，开销大且极为生硬。

## 2. 核心构想：会话与场域驱动 (Session & Field Driven)
将交互从“指令驱动”转变为“会话握手”与“场域驱动”，并深度结合现有的 `Premise` 与 `Settle` 属性架构。

### 2.1 交互会话 (Interaction Session)
“交互会话”是角色之间建立的**契约**。任何涉及双人或多人的持续性互动，都必须建立在 Session 之上。
*   **状态共享**：Session 统一管理当前交互处于哪个阶段，由专门的 `Handler` 负责推进。
*   **数据隔离**：交互产生的临时变量（当前阶段、轮到谁说话、游戏比分、氛围值）均存放在 `Session.data` 中，而非角色本体属性中。
*   **平滑结算**：摒弃瞬间的一次性属性结算。将大额的属性变化拆分至 Session 的每个 Tick（如每分钟）中渐进式生效（例如逐步降低疲劳、逐步恢复饱食度）。

### 2.2 社交场 (Social Field)
“社交场”是 Session 在地理空间（Scene）上的投影。
*   **可见性与氛围**：场域对外散发信息（如“A和B正在热烈讨论”），并具有核心属性 `atmosphere`（氛围值），不仅影响参与者，也会辐射到同一场景内的旁观者（如争吵产生压力）。
*   **开放性与干涉**：定义其他人是否可以旁听、是否可以随时加入（如开放的牌局 vs 私密的告白）。玩家或高权重 NPC 可以通过 `join_session` 主动介入。

### 2.3 握手与响应协议 (Handshake Protocol)
重构行为选择逻辑，禁止单方面强制拉取，改为“请求-评估-响应”机制：
1.  **社交请求 (Request)**：角色 A 决定发起交互，创建包含权重的会话请求（如赋予权重150的聊天请求），推入目标 B 的信箱（`social_requests`）。
2.  **权重竞争 (Evaluate)**：目标 B 在下一次 AI Tick（`character_behavior.py`）时，对信箱中积累的请求进行排序，并与当前正在进行的行为权重进行比对。
3.  **最终响应 (Response)**：
    *   **接受 (Accept)**：如果请求权重胜出，B 正常结束（或中断）当前行为，双方切换至 `STATUS_SOCIAL_INTERACTING`。
    *   **拒绝 (Reject)**：如果被拒绝或超时，发起方会调用 `handle_reject_social_request` 释放等待者，清除无效 Session，重新演算行为。

## 3. 技术框架实现现状与思路

目前游戏已正式接入此框架，完成了底层解耦与核心业务逻辑的迁移。核心数据结构及接口分布如下：

### 3.1 数据结构设计 (`Script/Core/game_type.py`)
核心类 `InteractionSession` 已整合在 `Cache` (`cache.interaction_sessions`) 中：
*   具有 `uid` (唯一标识)、`initiator` (发起者)、`members` (参与者列表)、`type` (枚举对应 `constant.Behavior`)。
*   具有 `data` (字典，存放交互阶段的临时数据)、`start_time` 与 `is_pending` (握手状态)。

角色本体 (`Character`) 中已挂载：
*   `social_requests`: 用于接收握手请求的列表 `List[Dict]`。
*   `active_session`: 当前正在参与的 Session UID。
*   场景 (`Scene`) 中新增了 `social_fields: Dict[str, str]` 记录当前房间内开展的会话以供 UI 渲染。

### 3.2 会话处理器工厂 (`Script/Design/session_handler.py`)
使用工厂模式和策略模式彻底解耦了各类行为的结算逻辑。由 `get_session_handler` 派发实例，基础接口 `BaseSessionHandler` 规范了生命周期：
*   `on_start()`: 握手成功后初始化（如初始化 `atmosphere`，设置比分、玩家顺位等）。
*   `on_update() -> bool`: 全局 AI 每 Tick 调用，处理游戏时钟内的阶段跳转和渐进式 `Settle`。返回 `True` 触发结束销毁。
*   `on_member_join(char_id)` / `on_member_leave(char_id)`: 动态增减员处理接口。

*   [x] 角色的属性扩充（`social_requests`, `active_session`）。

### 阶段二：握手协议与 AI 整合 (AI Handshake Protocol) 【已完成】
*   [x] 废弃原先直接修改 target state 的底层函数。
*   [x] 角色 AI 演算时，引入信箱请求与常驻行为树的绝对权重对比（`character_behavior.py` 中处理 best_request）。
*   [x] 闭环的“拒绝 (Reject)”处理：实现 `handle_reject_social_request` 释放等待者，销毁过期 pending session。

### 阶段三：群体社交与玩家接入 (Group & Player Integration) 【已完成】
本阶段旨在解决玩家体验层面的生硬感，以及建立最初的多人同框概念。
*   [x] 支持 3 人以上的 `InteractionSession` 注册与校验。
*   [x] “社交场”在场景地图界面内的可视化渲染（`Script/UI/Panel/in_scene_panel.py` 中展示 Social Fields）。
*   [x] **玩家主动加入**：场景面板中实装 `join_session` 按钮，玩家可作为第三人介入正在进行中的 NPC 会话。
*   [x] **AI侧发起的请求异步化**：AI通过赋予高权重并发送 request 来触发对话，取代原有的瞬发 `state` 篡改。
*   [x] **玩家发起的交互重构 (UI与异步表现)**：
    *   **机制**：玩家向 NPC 发起的互动已全面转化为 Request 推送。玩家下达指令后会进入 `STATUS_SOCIAL_INTERACTING` 等待状态，系统通过时间快进交由目标进行异步权重响应。
    *   **UI表现**：添加了拒绝的文本提示（“互动邀请被忽略或拒绝了”），通过文本界面流转呈现等待和拒绝反馈，替代传统的画面遮罩。
*   [x] **玩家离场与会话保持**：玩家通过“移动”操作离开当前房间时，应优雅地触发 `on_member_leave` 退出自身，而保证原会话内其他 NPC 继续互动。

### 阶段四：深度内容填充与专用 Handler (Content Expansion) 【已完成 / 持续扩充】
基于成熟的 Session 框架，各特定场景的高级玩法逻辑已初步实装于 `session_handler.py` 中，支持深度的渐进结算：

*   [x] **基础双人闲聊 (ChatSessionHandler)**：
    *   **逻辑**：每 5 分钟游戏时间推进一个 Stage，氛围值随机波动。
    *   **结算**：阶段性扣除疲劳度，完成阶段后才触发真正的 Settle。
*   [x] **课堂教学系统 (ClassroomSessionHandler)**：
    *   **逻辑**：每分钟 tick 演算。教师角色每 Tick 稳定增加疲劳消耗。
    *   **结算**：预留了参与的学生基于课程目标提升对应学科属性的空间。当教师状态改变时，课堂自然解散。
*   [x] **多人聚餐与宴会 (DiningSessionHandler)**：
    *   **逻辑**：同桌聚餐。每分钟恢复参与者的饱食度 (-2) 和口渴度 (-2)。
    *   **氛围**：席间有 20% 概率触发随机话题，增加聚餐整体的 atmosphere 氛围值。
*   [x] **博弈与娱乐活动 (GameSessionHandler)**：
    *   **机制**：`session.data` 完整存储了回合拥有者 (`turn_owner`) 和双方比分 (`scores`)。每分钟演算一次回合得分 (1~5分) 并交替发牌权。
    *   **结算**：参与者随时间持续降低疲劳度（获得娱乐值）。一方得分超过 50 时触发 Game Over 销毁会话。
*   [x] **冲突与争吵 (ArgumentSessionHandler)**：
    *   **机制**：初始设定为极低氛围值 (0)。不仅会场内成员高速增加疲劳与压力 (+0.5/min)。
    *   **场域辐射**：对当前场景内的旁观者（非 session members）造成环境污染，所有路人都会增加压力值 (+0.1/min)，生动呈现了“周围人在吵架让我很不舒服”的社会学模型。

### 阶段五：异常处理与边界条件 (Edge Cases & Fallbacks) 【系统健壮性保障 / 已完成】
*   [x] **强制中断清理 (Force Interrupt)**：当 Session 成员遭遇更高维度事件（如被攻击触发战斗、饿晕或剧情强制传送）时，状态机被强行切出。目前在 `update_social_sessions` 中已完善对失踪/位置变动人口的扫描，并安全调用 `on_member_leave`，支持群组会话在个别成员离开时继续保持。
*   [x] **无响应挂起保护**：防止出现极端情况下 NPC 一直处于 Pending 假死的状态，已在系统级主循环中加入严密的超时垃圾回收机制（Pending > 5分钟自动回收）。

### 阶段六：进一步的UI与表现层设计 (UI Polish) 【前端表现提升 / 部分完成】
*   [x] **更直观的参与者列表**：已实装基于行为类型的展示格式，例如 “【闲聊】A, B (氛围: 50)”。

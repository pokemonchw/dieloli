游戏底层交互系统技术架构
1. 整体架构概述
游戏的时间推进是事件驱动与时钟跳变相结合的（Tick-based）。每当角色（玩家或AI）执行一个带有持续时间的指令（Target/Instruction），游戏时间会按分钟进行步进（update.game_update_flow）。
在时间步进的切片中，所有的互动底层均统一封装为如下流水线：
状态判断 -> 目标检索(寻路) -> 设定行为 -> 时间流逝 -> 触发事件(Event) -> 属性/关系结算(Settle)。
---
2. 玩家与 NPC 交互逻辑 (Player to NPC)
玩家与NPC的交互主要通过 UI 触发指令池中的指令（Instruction），然后通过游戏的统一时间片进行结算。
2.1 目标确立与指令下发
1. 场景交互面板（in_scene_panel.py）: 当玩家身处某个场景时，UI系统会遍历当前场景中的所有角色实体，将其呈现给玩家。玩家在 UI 上指定一个 target_character_id。
2. 指令派发（instruct/目录）: 玩家点击某个互动（如闲聊、辱骂、H行为等），UI 会将指令推入指令队列（instruct_queue）。
   - 以“闲聊”为例（instruct/dialogue.py中的 handle_chat）：
     - 将玩家的行为 ID 设置为 constant.Behavior.CHAT
     - 持续时间（Duration）设为 10 分钟。
     - 将玩家当前的状态（State）设为 STATUS_CHAT。
     - 调用 update.game_update_flow(10)，步进10分钟。
2.2 事件触发与结算 (Event & Settle)
1. 时间推演: 游戏推进的这10分钟内，所有NPC都会积累生理状态（如口渴度 status[28]、饥饿度 status[27]、疲惫度）。
2. 触发交互事件: 时间到达玩家行为的结束时间（end_time）后，系统调用 event.handle_event 触发结束事件。
   - 系统读取 game_config.config_event_status_data[behavior_id]，筛选出符合当前前提（Premise）的交互事件。
3. 副作用执行（Settle Behavior）:
   - handle_settle_behavior 处理各种副作用。比如当发生聊天交互时，执行 handle_let_target_chat_self （位于 Script/Settle/interaction.py）。
   - 该函数会强制打断目标 NPC 原本的行动，强行把 NPC 的 target_character_id 指向玩家，状态置为 STATUS_CHAT。
   - 随之伴随结算系统的其他函数，变更 NPC 对玩家的好感度、修改心理参数（Humanity/Mind）、增加经验和增减体力等。
---
3. NPC 与 NPC 交互的算法与逻辑
NPC拥有完全自主的AI。它们与其它 NPC 之间的交互算法基于前提计算（Premise Checking）和加权随机（Weighted Random）。
3.1 状态校验与空闲判定
在每次时间步进时，系统会调用 init_character_behavior()：
1. check_character_status_judge: 检查NPC状态。如果NPC非死亡状态且当前为“闲置（STATUS_ARDER）”，AI 就会启动目标查找机制。
2. 如果 NPC 正处于某种行为中且时间已走完，则执行状态结算，然后变回闲置。
3.2 基于前提的目标检索与加权算法 (Target Search)
NPC的互动意向存储在 data/target/default.json 中。
1. 检索范围: search_target() 会遍历所有的可用目标（如“找喜欢的人聊天”、“去操场散步”、“逃避人群”）。
2. 前提筛选（Premise Validating）: 
   每一个 Target 都带有一系列前提要求。例如“和喜欢的人聊天”要求：
   - have_like_target_in_scene: 1 （场景里有喜欢的人）
   - not_in_class_time: 1 （当前不在上课）
   系统逐一校验这些前提是否满足，不满足的目标直接抛弃。
3. 优先级与权重累加（Weight Calculation）:
   - 基础权重：受到行为优先级限制（needs_hierarchy），越紧急的行动基础权重可能不同。
   - 性格/偏好加成：通过查找 NPC 数据中的 like_preference_data 或 dislike_preference_data 进行修正。喜欢的事物会增加选中权重，反之则降低。
4. 决策分配: 在通过了前提测试的列表中，根据权重概率池 value_handle.get_rand_value_for_value_region 随机选中一个目标指令。
3.3 寻路与状态机流转 (Pathfinding & State Machine)
选定目标后，AI 执行该目标绑定的状态机（state_machine_id）。
1. 寻路交互: 
   - 若交互对象在其他场景，触发 move_to_like_target_scene 这类的寻路机器（Script/StateMachine/pathfinding.py）。
   - 寻路器内部调用 character_move.py，根据地图节点使用 Dijkstra 算法（dijkstra.py）算出行动时间并开始转移场景。
2. 场景内交互:
   - 若已经在同一场景且准备实施互动（例如 CHAT_RAND_CHARACTER 位于 Script/StateMachine/interaction.py）：
   - 系统会在场景的人员名单 scene_data.character_list 里随机抽取一个除自己以外的对象。
   - 随后锁定该对象为 target_character_id，将自身状态变为交互态并设定好时长（Duration）。
   - 等待时间走完后，与玩家互动一样，触发事件系统的 settle_behavior 去拉取另一个 NPC 的状态，并双向结算好感度、心情等数值。
---
4. 特色系统：交互文本的大语言模型(LLM)动态生成
在结算 Player 与 NPC 乃至 NPC 自身交互的具体表现时，本游戏不仅支持传统的拼接字符串，还内建了接入外部 AI 模型（Ollama/OpenAI）生成动态事件文本的机制。
实现路径 (Script/Design/event.py):
1. 状态提取: 当 handle_event 发现存在有效的事件互动结束时，会提取出当前互动的关键要素：
   - npc_name: 角色名称
   - action_text: 动作名称（如“闲聊”、“辱骂”等状态）
   - start_text / end_text: 原有的固定文案
   - premise_text_list: 当前互动达成的环境与前提清单
2. Prompt 拼装: 根据内置的 prompt 模板进行格式化（基于 normal_config.config_normal.prompt）。
3. API 请求:
   - 玩家若启用了 ai_mode == 1：调用本地 Ollama 生成润色后的文字。
   - 玩家若启用了 ai_mode == 2：通过 openai 库请求远端大模型生成。
4. 回填 UI: 将大模型产出的动态描写采用正则剔除思维链等杂讯后，拼接到 UI 面板（now_event_draw.text）进行展示，从而实现不重样的沉浸式交互表现。
